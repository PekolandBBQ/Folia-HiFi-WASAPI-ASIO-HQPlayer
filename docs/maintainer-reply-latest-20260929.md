## 一、组件形式与长期维护

### 1. 辅助程序源码、构建和发布放在独立仓库

我已完成拆分。独立组件负责 .NET/NAudio、WASAPI/ASIO、设备和 PCM 输出；宿主只保留安装管理、进程监管、音源准备、播放适配和设置入口。普通 Folia 构建不编译 .NET，也不要求用户安装 .NET SDK。

本轮运行组件为 0.1.2，组件源码提交 `a6a073f`。源码、构建和测试已分离，但候选 ZIP 的本地验证不等于正式组件 Release 已发布；正式发布流程仍需完成。

### 2. 接口稳定、标明版本并提供 RFC

我已提供协议 v1 RFC。连接时校验协议主版本、组件版本和所需能力；破坏性变化需要升级协议主版本，不兼容时拒绝开启原生后端。组件只接收本地 PCM，不接触流媒体账号、Cookie 或提供商 API。

### 3. 未安装组件的用户不应受影响，也不需要另一套应用或音乐库

主线接入方案使用 Folia 原有应用标识、设置和音乐库，组件缺失时保留浏览器播放。我已验证停用组件后的 Web 路径，并以未修改的 v0.7.9 完整 App 做对照，覆盖播放、定位、暂停续播、错误恢复、循环、ReplayGain 和双甲板交接，两边共 18 项通过。

我进一步统一了设置模块、侧栏和相关命令的环境判断：只有 Windows 桌面端、当前进程架构受支持（目前 x64）且原生 IPC 桥可用时才显示入口。macOS、Linux、普通浏览器及不受支持的环境自动隐藏这些配置；兼容 Windows 未安装组件时保留安装入口，不把“缺少组件”和“系统不支持”混为一谈。

我也修正了组件未安装或已停用时，选择缓存设备列表中的 WASAPI/ASIO 却没有反馈的问题。设备选择、自动回退、整数直通及显示音频链路都在操作前重新查询组件状态；不可用时，设置界面提示安装，命令面板引导到对应设置，不保存无效选择，也不因被拒绝的操作暂停当前播放。没有已批准安装源时说明原因；安装失败可重试，成功后重新选择才生效。

用于审查的上游接入方案仍复用原应用和音乐库。另外，我在自己的 fork 中独立维护 Windows 专版 **Folia-HiFi-WASAPI-ASIO-HQPlayer**，使用独立配置目录，随包提供固定哈希的离线组件。它用于在上游暂不合入时供个人和其他用户试用，不要求主线采用专版应用标识；专版入口也没有迁入 A/B/C 审查增量。

### 4. 能否跟进每周一到两次主线更新，不阻碍正常发布

我愿意跟进主线每周一到两次的更新，负责组件及对应接入代码的适配，主线影响播放、automix 或本地库时同步回归。本轮已实际整合 v0.7.9，并完成基线对照和发行件验证。

不能及时适配时，应停用不兼容的可选原生能力、保留浏览器播放；组件发布任务不应成为普通 Folia 构建的前置依赖。本轮结果能说明当前版本的适配情况，不能代替未来每次更新的维护工作。

### 5. 用户报错后的响应和经过测试的修复

我愿意在用户报错后收集日志、格式协商、设备和复现条件，提供经过测试的通用修复。这次根据实际失败修正了首次播放意图丢失、晚到缓存恢复覆盖用户选曲、安装清理失败导致 busy 不释放，以及临时文件占用导致更新失败等问题；失败和修复后的证据都保留。

最近的人工使用反馈还暴露了组件缺失时的无响应选择，以及其他桌面系统也可能显示 Windows 专用入口的问题。我已修正，并补充了状态失效、安装失败／重试／成功、平台与架构可见性的回归；具体新增测试及边界见第 22 项。

完整硬件矩阵目前限于 XingCore。其他 DAC/ASIO 驱动需要独立验证，不能把本机通过扩展为所有设备兼容承诺。

### 6. 是否愿意加入贡献者团队，长期负责组件及接入代码

我愿意加入贡献者团队，长期维护组件和对应接入代码。是否加入团队及实际协作方式仍由双方确认，不把测试通过表述为已经加入团队或获得合入批准。

## 二、音频后端、浏览器隔离与精度

### 7. 浏览器模式不应受原生错误处理、deck 绑定等改动影响

原生专用错误处理及输出资源管理已限制在原生后端或后端切换边界。涉及共享播放生命周期的修正另外进行了未修改官方版对照，没有只测试孤立 transport。

完整 UI/截图套件 275 项通过；此外，真实 QQ 音源的完整 App 非 plain automix 已观察到两甲板同时播放、约 7 秒 cue 和自然进入下一首。此处证明的是浏览器路径回归结果，不把 Web automix 的效果推定为原生路径已经支持相同的无缝混音体验。

### 8. 移除 Gyan 构建，复用官方裁剪 FFmpeg，并单独提 PCM 编码 PR

我已移除额外 Gyan 构建/下载方案，沿用宿主 FFmpeg 位置；PCM24 和可选整数路径需要的 PCM32 已作为 [folia-ffmpeg-build PR #1](https://github.com/chthollyphile/folia-ffmpeg-build/pull/1) 单独提交。

**本次重新核对的最新状态：PR 已于 2026-09-27 06:29:58 UTC 合并，上游随后发布了 [v8.1.2-folia.2](https://github.com/chthollyphile/folia-ffmpeg-build/releases/tag/v8.1.2-folia.2)。** 因此旧文档中“仍待 FFmpeg 补丁合并/发版”的说法已过时。

仍需区分宿主集成状态：核对时 Folia `main` 的 `packaging/ffmpeg/fetch-ffmpeg.mjs` 仍固定 `.1`；本轮官方 0.7.9 安装包中的 FFmpeg 也仅检测到 PCM16 编码器。已交付的验证包使用经校验的本地 PCM24/PCM32 候选，不冒称已用官方 `.2` 二进制重跑全部矩阵。剩余工作是更新宿主固定版本/哈希，并对官方产物复测。

### 9. WASAPI 补充 WAVEFORMATEXTENSIBLE 格式协商

我已补充相应协商。组件测试覆盖 extensible-only、拒绝和候选顺序，共 7 项格式测试通过；真实 XingCore 的 WASAPI/ASIO 播放另有实机记录。不支持格式时明确失败，不静默改采样率或降到共享模式。尚未覆盖所有只接受该格式的 USB DAC。

### 10. 普通命令错误不应释放整个播放引擎

我已按命令类型和 session 归属收窄释放范围。设备枚举、参数/增益、握手及旧会话错误不会直接停止当前播放；当前会话的加载或播放控制失败才清理相应资源。

20 项组件错误隔离测试通过，并在真实播放期间验证 devices 和旧 session 失败后当前时钟继续运行。

### 11. 保留 ReplayGain

我已保留既有 track/album/off、峰值保护、音量和静音语义。完整 App 已覆盖真实 FLAC 标签 → 导入文件夹 → 生产扫描/metadata worker → IndexedDB → 重载 → 切歌 → 实际引擎的链路：两后端 × 两处理模式 × 三策略 × 两文件，共 24 步通过；另有持久缓存、专辑标签缺失回退等针对性用例。

整数模式也保留增益控制，不强制最大音量；只有特定单位增益条件下才描述准备后的 PCM 采样值保持，不将整数模式等同于整条链路 bit-perfect，也没有做 DAC 模拟输出的逐位证明。

## 三、在线源是否可以纳入 v1

### 12. Node fetch 不带应用会话 Cookie

我已将生产下载路径改为使用发起播放的 Electron session 的 fetch，并包含凭据；生产路径缺少该能力时明确报错，不退回无会话的 Node 下载。

我已用实际 Electron session 和受保护端点做“无 Cookie 拒绝、有 Cookie 成功”的独立对照。三平台真实播放另有记录；没有用“歌曲播放成功”代替必须携带 Cookie 的证明，也不导出账号 Cookie。

### 13. 现有链接刷新、各平台播放及过期恢复

我保留了既有音源解析、账号权限、音质选择、缓存和链接刷新流程，组件不直接调用提供商接口。网易云、QQ、酷狗分别在 WASAPI/ASIO 上验证，每个平台 10 步，共 30 步通过，包含真实 HTTP 403、受控媒体失败、非零进度恢复、暂停意图及连续失败后停止重试。

这里采用受控失效/拒绝方式验证恢复，没有等待每个平台的 URL 自然过期。HTTP 403 与非零进度媒体失败是不同用例，不将两者合并描述成一条未执行的测试。

### 14. Navidrome、folia-transcode 与严格／容错并行解码

我已验证完整 App 原播放 → 故障事件 → 自动转码 → 恢复链路，双后端正常转码 4 步通过。

对曾经首次播放停在 paused/IDLE 的问题，本轮复现了 StrictMode 重建 transport 丢失播放意图，以及晚到启动恢复覆盖用户选曲的竞争，并分别修正。保留失败/通过截图和调用时序。最早那次历史失败缺少同等级调用栈，不能追溯断言它必然属于其中某一根因。

我确认两首重点曲目 `HUMMING LIFE — Spica`、`ピコ — 桜音` 的现有 FLAC 存在坏帧，保留了原件。为了缩短串行失败后再重试的等待，我将恢复逻辑改为共享一次下载，并行准备严格和容错输出：严格成功优先，严格因音频损坏失败时选用通过完整严格输出校验的容错结果；非音频错误不会因此被忽略。切歌取消两路旧作业，不无限重试。服务每次只处理一个恢复作业，作业内最多两个编码进程；普通健康播放不会启动这对进程。

我完成了两曲 × 播放/暂停 × 浏览器/WASAPI/ASIO 的 12 项冷恢复检查，全部通过，同曲、位置及暂停意图保持，无错误 toast。同一输入的三轮串行／并行交替测量中，Spica 的处理时间中位数从 847.8 ms 降到 521.7 ms（缩短 38.5%），桜音从 784.9 ms 降到 488.5 ms（缩短 37.8%）；该测量排除网络和设备打开时间，缓存命中也另行记录。完整 App 冷恢复约 0.66–1.00 秒，仍可能有可听停顿。因此我将当前效果表述为“自动容错同曲恢复并缩短等待”，不称为完全无感或无缝播放；容错可能丢弃坏帧，也不等于修复源文件。

### 15. 在线源的 v1 范围与整数模式、链路展示拆分

在线范围仍是完整准备音频后播放，不是新增流式原生解码；有首次等待、临时磁盘占用及硬件覆盖边界。现在已有逐源的 App 证据，供你判断是否足以纳入 v1；最终接纳范围仍由审查决定。

我已将整数模式和链路展示拆成依次叠加的本地审查分支。以下快照已迁入并行解码等基线修正，但尚未包含后续 `269dab8` 的环境检查、安装提示和改名：

## 四、组件协议、分发与错误恢复

### 16. 兼容的旧组件保留在清单，有新版只提示更新

我已实现兼容目录保留校验，不因有新版就让已安装旧版变为未安装。已验证真实旧组件配新宿主播放、更新提示、上一版恢复播放；失败时保留旧激活指针。正式生产批准清单目前仍为空，测试使用固定候选，不把它说成线上分发已经可用。

### 17. 固定错误码、前端翻译、原文只进日志

响应和错误事件使用固定 `errorCode`，前端按码显示翻译后的提示，不展示原始 .NET 异常。原始诊断只进日志，包含 URL/凭据脱敏；本轮补充了 helper stderr 的实时、限长诊断，避免只能在进程退出后才看到错误。

最新的缺失组件和安装失败提示也沿用同一规则。我已验证安装失败时显示翻译后的固定错误码，不把原始诊断文本直接放入弹窗，并保留重试入口。

### 18. 由 Folia CI 校验并镜像发布，客户端下载地址只指向 Folia

工作流已按此边界编写：固定候选版本和哈希 → 校验/握手 → 上传 Folia Release，客户端清单只接受 Folia 地址。修正了发布准备任务未依赖校验任务的问题，`prepare-mirror` 现在依赖 `verify`。

本地目录/工作流检查通过，但官方候选批准、独立组件正式发版、Folia CI 下载和镜像上传尚未完成。`verify-component.cjs` 对空正式清单返回 PENDING，这不是正式下载验证通过；没有冒称运行了维护者环境的远程发布流程。

### 19. 暂停可以释放输出，并写明状态事件频率

RFC 已改为暂停时允许释放输出，保留未来保持设备打开的空间，不把释放设为必须遵守的语义。当前实现每 40 ms 尝试发送一次状态，约 25 Hz；命令响应也可携带状态，前端不能假定固定到达间隔。

### 20. 组件崩溃/超时后的行为

RPC 期限为 15 秒，超时终止故障进程。`COMPONENT_CRASHED` / `COMPONENT_TIMEOUT` 默认提示并回退浏览器；关闭自动回退后，提供重试、默认播放和上一版本三个操作。不会在清理过程中无限自动重启；恢复受歌曲身份和请求代次保护，过时任务不能抢回播放。

我已用真实 helper 终止和受控 RPC 阻塞验证默认/手动恢复、非零位置和暂停意图，并保留实际交互截图。音源失效、转码失败走各自恢复流程，不伪装成组件崩溃。

### 21. 磁盘只保留当前版和上一版

我已限制版本保留并保存停用后的可恢复指针。安装/停用先释放原生使用，更新失败不切换旧激活指针。

补充了 7 类 Windows 异常：active 指针锁、归档独占锁、旧 exe 运行中、待清理 exe 锁、staging 清理锁，以及 active 写入前/后中断安装进程。修正清理异常阻止 busy 释放和间歇 rename 失败；仅对指定占用错误有界重试，最多 6 次，总等待 1.5 秒，持久锁仍明确失败。完整候选连续三轮 21 项通过，A/B/C 各 7 项通过；占用暂时阻止清理时不能承诺立即删净所有旧文件。

### 24. 独立维护版及 HQPlayer 扩展的边界
