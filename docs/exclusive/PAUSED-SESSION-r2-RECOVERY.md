## 用户日志定位

提供的 2026-10-15 日志中，北京时间 16:22:53–16:32:40 连续七次返回 `PAUSED_SOURCE_COMPLETE_SESSION_PROOF_REQUIRED`，涉及《レイン》《Hello,Again》《ザイオン》及后续选曲。换歌请求仅约 10–14 毫秒即失败，说明后续点击没有重新完成暂停观察。

代码存在两个相连问题：进程采集仍把 Windows render session 的 Active 标记当作暂停条件；清理失败后提前关闭控制会话，并永久复用失败 Promise。最初那次失败的具体原生子条件未进入用户常规日志，不能事后断言一定是 Active 超时。

## 实现

- 进程采集的暂停保持使用新鲜的 Spotify 暂停/曲目/设备/进程事实，以及确切的采集停止回报。Windows render client 保持 Active 不再阻断它。空播放器恢复仍需原生静止证明。
- 停止阶段不再用暂停前缓存的静音占位会话快照否决已确认的采集停止。续播仍刷新采集基线并建立新的采集区间，不能把删除暂停检查当作省略续播准备。
- 路由事务在进程采集模式不要求活动音频出现在 VB 端点混音中。旧端点采集模式维持原规则；进程身份、会话快照完整性/新鲜度、路由所有权及恢复记录继续校验。
- 可恢复的暂停确认失败保留同一控制会话和路由记录；新的播放请求重新执行清理，成功确认停止并保持暂停后清除旧失败。清理中的重复调用仍共享进行中的工作，不并发抢占。恢复写入尚未开始的暂态原生暂停失败，也可由确切恢复回报发起重试。
- 暂停诊断细分为仍活动、超时、扫描不完整、进程不一致、快照过期、时间超前和缺少实例标识。中文提示保留操作阶段和机器码。常规运行日志新增 `SpotifyCleanup` 的 `cleanup-failed`、`cleanup-retry`、`cleanup-recovered`，避免只在可选冷启动日志中留下原因。最终实播后的传递检查还补齐了“新采集基线尚未建立”的既有错误码，让其经过路由、公共错误和日志各层时不再退化成泛化提示；此项只改变诊断枚举，不改变播放逻辑。

## 保留的失败与证据限制

开发候选的失败均保留：跳过暂停扫描后暴露旧占位快照拦截、未刷新续播基线，以及 HQPlayer 退出独占设备后旧端点目标活动检查导致 ASIO 失败。最后一项曾使该候选无法正常退出；停止已无采集/路由子进程的测试应用后，由下一候选沿原恢复记录自动恢复。均不计为通过。

最终候选首次 inspect 保留 `ORIGINAL_ENDPOINT_UNSAFE`，约 579 毫秒后记录原路由自动恢复，随后正常播放。最终退出过程中，旧 status 查询与采集释放重叠，保留一次 `SESSION_OBSERVATION_UNTRUSTED`，其后暂停保持、精确恢复及退出完成均成功；不称日志零错误。

软件非零 PCM 与输出时钟不能替代 DAC 波形或人工听感。本轮不宣称爆音根因已解决，也不重新判定三秒性能或偶发 Seek。原始用户日志含账号资料，仅留本机；公开验证包只含整理后的有界证据。
