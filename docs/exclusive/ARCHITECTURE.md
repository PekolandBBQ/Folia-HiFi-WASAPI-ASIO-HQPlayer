# 架构、测试与上游接入约束

我将专版发布与上游接入分开维护。正式版表示这个 fork 的发布状态，不代表作者已批准组件、镜像源或 PR，也不替代每次更新的真实测试。

## 模块与审查边界

| 审查单元 | 职责与依赖 | 拆分限制 |
| --- | --- | --- |
| 独立音频组件仓库 | .NET/NAudio、WASAPI/ASIO、PCM 输出、协议 v1 | 不含账号、Cookie、在线服务 API；普通 Folia 构建不编译 .NET |
| A：宿主基础接入 | 组件管理、协议与进程、音源准备、ReplayGain、恢复、环境检查 | 未安装组件仍可正常使用浏览器；不含专版品牌、配置迁移、HQPlayer 或整数/链路独有 UI |
| B：整数处理 | 在 A 上增加整数 PCM 处理与对应设置 | 使用独立增量提交，保留音量、静音和 ReplayGain，不强制最大音量 |
| C：音频链路 | 显示后端实际报告的格式、增益 | 显示层不控制播放或安装组件；未报告数据不伪造。历史 C 基于 B，移交 PR 时明确这个依赖；若改为只依赖 A，必须重新生成 diff 并复测，不能直接宣称互相独立 |
| D：HQPlayer | `hqplayerHost/Protocol/Discovery/Session` 与独立设置；复用宿主播放适配 | 不依赖 WASAPI/ASIO 组件安装。公共 transport/service 的接线作为单独接入增量，不能把删除几个模块文件当作已验证的功能移除 |
| E：专版分发 | `packaging/exclusive`、安装程序、离线目录、品牌、配置迁移 | 只由专版启动入口加载；上游 `electron/main.cjs`、默认 appId 与配置不依赖它，不进入 A/B/C |

现有 A/B/C 是前轮快照，尚未包含全部最新设置修正。提交上游前，通用环境检查放入 A，整数开关检查放入 B，链路检查放入 C；对每个实际提交单独测试并给出比较基线。HQPlayer 和专版分发未经同意不混入这些 PR。源码分层和可拆分设计不等同于最新 PR 已准备完毕。

## 每次更新必须完成的检查

1. 读取最新上游稳定 Release、作者新增意见、README、相关 skills 和 CI；记录基线提交。`release.json` 的软件版本、上游基线版本与 `package.json` 保持一致，专版标签使用 `hifi-v<上游版本>`。
2. 保留上游完整门槛：根目录 `npm run typecheck`、`npm run test:unit`；sync-server 的 `npm ci` 和 `npm run build:node`。沿用 `.github/workflows/pr-unit-tests.yml`，专版分支也触发，不能替换为仅跑新增测试。
3. 设置/交互按上游 testing-strategy 做 Playwright 回归；专版 CI 额外运行相关组件 UI。涉及共享浏览器播放、automix、在线源、缓存或 ReplayGain 时扩大到完整 App 对照；不能拿模拟 IPC 代替真实设备。
4. 协议/组件改动要重跑握手、版本兼容、旧版保留、命令隔离、崩溃/超时和升级回退；安装变更重跑安装、覆盖、卸载和配置保留。每个实际发行件检查生产依赖、哈希及播放；本机硬件覆盖范围随报告列出。
5. 官方镜像必须先完成候选哈希/协议校验和批准，客户端下载地址仍依照上游要求。专版随包固定哈希目录不等同于官方批准源，不能迁入上游默认路径。
6. B/C/D 使用清晰增量，按各自基线运行类型、单测、相关 UI/硬件检查；不沿用另一个分支的“通过”结论。任何未执行项标记待办，失败保留原始证据，修复后再复测。
7. 发布源码、使用说明、原始证据与校验值；普通用户首先看到安装 EXE / ZIP。未来每次更新重新执行上述检查，不以这次通过承诺未来无回归。

当前自动边界测试位于 `test/unit/exclusive`：软件版本对齐、上游默认入口和品牌隔离、HQPlayer 控制模块不依赖原生组件安装，以及配置迁移的数据保留。它们是持续检查的一部分，不能证明所有架构要求或硬件组合均成立。

作者要求的来源及逐项现状见 [统一回复草稿](../maintainer-reply-latest-20260929.md)，仍未向作者发送。
