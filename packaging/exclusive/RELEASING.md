# 专版双源发行附件保留规则

维护者于 2026-10-19 明确授权每次 Gitee 发布均执行以下规则。

1. GitHub 保留完整历史发行件；Gitee 只保留最新正式版的大型安装包和便携包附件。
2. 发布前确认旧版完整 EXE / ZIP 在 GitHub 仍可下载，再删除 Gitee 旧版的 EXE、ZIP 及其分片。不可删除发行说明、标签、源码历史、本机配置或组件备份。
3. Gitee 旧版说明添加 GitHub 对应版本的下载链接。小型说明文件和更新清单可保留；应用更新接口应指向最新完整正式发行版。
4. GitHub 和 Gitee 使用同一次构建；Gitee 按既有清单分片。待全部预期附件上传完毕、清单名称和大小与附件列表相符后，再设为正式版，避免暴露不完整更新。
5. 只清理目标 fork 的 Gitee 附件，不操作上游仓库。上传失败时保留未完成发行版为预发行状态，按已上传附件续传，不重复删除或覆盖已有备份。

用户无需为每次旧包清理重新确认；若扩大为删除说明、标签、源码或 GitHub 历史包，则不在上述授权范围。

## 复用已装配目录时的必做步骤

替换 `resources/app.asar` 后、生成 EXE / ZIP 前，运行：

```powershell
node packaging/exclusive/syncDesktopScripts.cjs <候选目录>/resources
```

这一步从最终 ASAR 提取当前版本的四个 Spotify 外部脚本，更新 `spotify-wrapper/scripts`。不能仅复制 electron/dist/shared 后继续沿用旧资源目录：PowerShell 实际执行的是 ASAR 外的脚本。r6 曾因此漏掉商店版 `binaryVersion` 和进程启动参数发现，导致客户端升级后仍加载旧外部资源。完整构建的 extraResources 已复制这些输入；复用包必须执行同样的刷新。验证对象应为最终包中的脚本，而非只运行源码脚本。

### 固定重打包入口与发布记录

复用候选目录生成发行件时统一使用：

```powershell
node packaging/exclusive/repackage.cjs <候选 win-unpacked 目录>
```

该入口先同步最终 ASAR 的外部脚本，再生成 EXE/ZIP 及分片清单，不自动安装或发布。不再使用临时 installer 配置直接对旧目录执行 electron-builder。生成的 assembly-inputs.json 只记录装配输入，不能替代实播通过记录。

每次修复及发布记录必须分别填写：

- 实际失败证据：使用的版本/构建、入口、失败现象及已确认的根因。
- 受影响边界：源码、独立脚本、原生组件、包内资源、用户配置；说明哪些实际变化。
- 针对性回归：首次连接、既有配置升级、失败恢复中受本次修改影响的用例；写明模拟与实测。
- 最终产物验证：从候选 resources 运行真实脚本或组件，不仅运行源码副本；同一次构建用于便携包和安装包。
- 用户实播：结果、日志与仍待确认项目。没有完成则写待验证，不按测试数推定通过。
- 发布：PR/检查、发行标签、两个源附件是否齐全及已知问题。未变化且已有通过证据的项目不重复测试。
